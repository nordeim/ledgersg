## 2. Findings (verified, with evidence anchors)

### Medium

**E2E-P25-M1 — THE headline: the fresh-host first-run truth is broken — the §9 bootstrap does not deliver the substrate the P24-era e2e contract needs.**
Three verified symptoms on a fresh environment: (a) `apps/web/e2e/ledger.spec.ts:59` documents "The demo substrate posts 36+ journal lines (the §9 bootstrap)" but the bootstrap posts **6** (`scripts/bootstrap_demo_substrate_session40.sh` step 4 — one invoice + one credit note); the `P24/FE-P1` spec fails on `/Showing 1–20 of \d+ rows/` (11 lines after one e2e run — a single page). (b) The P7 void spec (`apps/web/e2e/invoices.spec.ts:284,291`) skips when no voidable document exists in the demo org — on the fresh first run the banking spec's settlement had PAID the only invoice by then (first run 1 skipped; second run 0 skipped — order/DB-state dependent). (c) The documented baseline "live e2e:full **42/42**" is therefore not reproducible on a fresh host (40P/1F/1S → 41P/1F/0S observed). Fix: **bootstrap step 4c — the pagination fodder top-up**: count the org's ledger lines (`journal-entries/ledger/?limit=1` → `count`, the P24 contract) and its APPROVED SALES_INVOICE stock; while lines < 36 or approved < 4 (max 12 iterations, defensive), create + approve a small fodder invoice (50.00 at the fiscal-year-start date, the step-4a conventions). Guarantees: ≥ 36 lines (the spec's documented claim, deterministic "Showing 1–20 of 36" → 2 live pages) and a durable voidable stock (≥ 4 APPROVED survive the banking spec's per-run settlement). Idempotent: a re-run at ≥ 36 lines / ≥ 4 approved creates nothing; the loop re-queries the count each iteration.

**BE-P25-M2 — a validly-typed but astronomically large offset is an untyped 500 on the ledger endpoint (the typed-400 convention violation).**
`apps/backend/common/pagination.py:122-126` validates offset only as a non-negative integer; `?limit=10&offset=99999999999999999999` passes parsing, then the SQL-level slice (`apps/journal/views.py` `queryset[offset:offset+limit]`) emits `OFFSET 99999999999999999999` → Postgres `DataError: bigint out of range` → **500** (live-reproduced through the running stack during the audit). Only `LedgerView` is affected (the five envelope views Python-slice — a huge int yields an empty page, 200). Violates the P7/F-11 garbage-param convention the module's own docstring claims. Fix: `parse_int_param` gains `max_value` (the additive mirror of `min_value`, P8/G-2); `parse_limit_offset` parses offset with `max_value=2**63 - 1` (int8 parity — the documented Postgres bound) → the typed 400.

**BE-P25-M3 — the transactions surface has zero pagination test coverage (the P24 commit message overstates "the five service-driven surfaces").**
`apps/backend/tests/integration/test_pagination_p24.py:279-286` — `URL_BUILDERS`/`TOTALS` cover entries/documents/contacts/payments only; no test exercises `BankTransactionListView` (the 26-test count confirms: 13 ledger + 4×3 surfaces + 1 tiebreaker). A regression in the transactions slice/envelope path would pass CI. Fix: extend the fixture with 3 `BankTransaction` rows (the `reconciliation_service.py` creation shape) and add `"transactions"` (`/api/v1/{org}/banking/bank-transactions/`) to the P25 test matrix (limit-slice + total-count + unpaginated envelope + garbage 400).

**FE-P25-L3 — the organisation-switch offset reset relies on timing internals (hardening, not a reproduced bug).**
`ledger-client.tsx:38-40` — the offset reset lived in a `useEffect` (post-commit): the first render after `orgId` changes calls `useLedger(newOrg, …, {offset: 40})`, and the reset lands one render later. **Empirically verified this session (the real-hook test): the stale-offset fetch does NOT manifest on the current stack** — React 19 + TanStack 5.90's notifyManager batching suppresses it (the old code never fires the stale URL) — so this is hardening, not a reproduced defect. Pinned by a dedicated real-hook spec (the transport URLs assert no stale offset for the switched org).

**BE-P25-L4 — `offset` without `limit` is silently ignored (the module's own "explicit beats silent" philosophy is contradicted).**
`common/pagination.py:110-126` — a well-formed `?offset=50` parses, then every view returns the FULL unpaginated set with the offset unused (live-verified: `parse_limit_offset` → `(None, 50)`); a caller that drops `limit` while paging gets the full set with no signal. (Garbage `?offset=abc` DOES 400 — the param is parsed then discarded only when well-formed.) Fix: the typed 400 when a non-empty `offset` arrives without a `limit` — the same surfacing convention as the limit range. **No existing consumer sends offset-without-limit** (verified: the e2e specs, the bootstrap, rls_smoke, and all five frontend hooks pass both or neither) — the API guide documents the rule (3.3.0 → 3.4.0).

**DOC-P25-L5 — two stale truths in the P24 slice.** `ledger-client.tsx:15-18` — the header comment says "page size 50 rows" while `LEDGER_PAGE_SIZE = 20` (line 24); `ledger-page.test.tsx:173` — the test name says "hides the pagination controls for an unpaginated single-page ledger" while the test (and its inline comment) assert the controls **stay** with Next disabled. ## 6. Open decisions (resolved with judgment)

- **The offset-without-limit semantic → the typed 400 (not silent-ignore, not auto-limit):** the module's own philosophy ("explicit beats silent clamping — a caller's paging bug must surface"); no existing consumer sends the shape (verified across the e2e suite, the bootstrap, rls_smoke, and the five hooks); the API guide documents the rule (a minor version bump — 3.4.0 — because request semantics change for a previously-200 shape).
- **The offset cap at 2^63−1 (int8 parity):** the natural documented bound — Postgres OFFSET is a bigint; anything larger cannot round-trip. A tighter cap (e.g. count-bounded) would need a per-request COUNT the unpaginated surfaces don't pay.
- **The bootstrap targets — ≥ 36 lines / ≥ 4 APPROVED / max 12 iterations:** 36 is the spec's own documented claim (restored to truth); 4 approved keeps the void spec deterministic for many runs (the banking spec consumes ~1 per run, and its helper creates its own when none outstanding); 12 iterations is the defensive bound against a pathological state (each iteration re-queries the count — no assumed line-per-invoice arithmetic).
